# AI 客户意向分析

## 1. 背景与目标

当前 CRM 已经具备客户、联系人、跟进记录、商机和合同等基础能力。本功能通过调用 DeepSeek、通义千问、智谱、OpenAI 等大模型，结合客户档案、历史跟进和商机信息，判断客户当前意向，辅助销售人员制定下一步跟进计划。

目标：

- 自动识别客户意向等级和意向分数
- 提取客户需求、痛点、预算、采购时间和决策角色
- 识别销售风险
- 生成下一步跟进建议和建议跟进时间
- 保留分析历史，支持追溯、重试和模型效果评估
- 支持切换不同大模型厂商，不让业务代码绑定单一厂商

## 2. 术语与边界

客户现有的 A/B/C 等级与 AI 意向等级含义不同：

| 字段 | 含义 |
| --- | --- |
| 客户等级 | CRM 人工维护的客户分级，A/B/C |
| AI 意向等级 | 基于近期沟通内容动态计算的高/中/低/未知意向 |
| 商机阶段 | 业务人员维护的销售流程阶段 |

AI 只提供判断和建议，不自动修改客户等级、客户状态、商机阶段或合同状态。销售人员可以采纳、忽略或人工修正 AI 建议。

## 3. 一期功能范围

### 3.1 分析触发

- 客户详情页手动触发分析
- 新增或修改跟进记录后触发分析
- 支持重新分析
- AI 调用失败不影响客户和跟进记录保存

### 3.2 分析结果

AI 结果至少包含：

- 意向等级：高意向、中意向、低意向、未知
- 意向分数：0～100
- 置信度：0～1
- 结论摘要
- 客户需求
- 客户痛点
- 预算信息
- 采购时间
- 决策角色
- 销售风险
- 下一步跟进动作
- 建议跟进时间

意向等级建议：

| 等级 | 分数 | 说明 |
| --- | ---: | --- |
| 高意向 | 80～100 | 有明确需求、预算、采购时间或积极推进信号 |
| 中意向 | 50～79 | 有兴趣，但需求、预算或时间尚未明确 |
| 低意向 | 1～49 | 需求较弱、回复少或暂无明确计划 |
| 未知 | 无 | 当前信息不足，无法可靠判断 |

### 3.3 前端展示

客户列表和客户详情支持展示：

- 当前 AI 意向等级
- 意向分数
- 分析摘要
- 最近分析时间
- 建议跟进时间
- 下一步建议
- 分析历史
- 立即分析和重新分析按钮

支持按 AI 意向等级、分数范围和待跟进状态筛选。

## 4. 分析输入

一次分析可以组合以下信息：

- 客户名称、行业、来源、备注
- 联系人姓名、职位
- 最近 5～10 条跟进记录
- 当前商机阶段、金额和预计成交日期
- 最近一次跟进时间
- 当前下次跟进时间

输入内容应限制长度，避免上下文过大和调用成本不可控。发送给第三方模型前，应按部署要求对手机号、邮箱等敏感信息进行脱敏。

## 5. 推荐分析结果结构

```json
{
  "intentLevel": "high",
  "intentScore": 82,
  "confidence": 0.88,
  "summary": "客户已明确表达采购需求，正在比较方案和价格",
  "needs": ["客户管理系统", "销售流程管理"],
  "painPoints": ["客户资料分散", "跟进记录不完整"],
  "budget": "未明确",
  "purchaseTimeline": "预计1个月内",
  "decisionRole": "可能为业务负责人",
  "risks": ["尚未确认预算", "可能存在竞品比较"],
  "nextAction": "3天内安排产品演示并确认预算",
  "suggestedNextAt": "2026-09-21T10:00:00+08:00"
}
```

模型输出必须经过 JSON 解析、字段校验和分值范围校验。无法解析时应标记为分析失败，不得将未经校验的文本直接写入业务字段。

## 6. 数据设计

### 6.1 当前意向表：`crm_customer_intent`

保存客户最新一次有效分析：

- `tenant_id`
- `customer_id`
- `intent_level`
- `intent_score`
- `confidence`
- `summary`
- `needs`
- `pain_points`
- `budget`
- `purchase_timeline`
- `decision_role`
- `risks`
- `next_action`
- `suggested_next_at`
- `analyzed_at`
- `provider`
- `model`
- `prompt_version`
- `status`

列表型和结构化扩展字段一期可使用 JSON 存储；用于筛选、排序的等级和分数使用独立字段。

### 6.2 分析历史表：`crm_customer_intent_analysis`

保存每次分析请求和结果：

- 客户、租户和触发人
- 输入内容快照
- 结构化分析结果
- 分析状态
- 错误信息
- 模型厂商和模型名称
- Prompt 版本
- 请求耗时
- 创建时间

历史表用于审计和效果评估，当前意向表用于高效查询。

## 7. 后端架构

### 7.1 Provider 抽象

定义统一的大模型接口：

```go
type LLMProvider interface {
    AnalyzeCustomerIntent(ctx context.Context, input IntentInput) (*IntentResult, error)
}
```

首期使用 OpenAI-compatible HTTP 适配器，通过配置切换 DeepSeek 等兼容厂商。后续如厂商协议不兼容，再增加独立适配器。

业务模块只依赖 Provider 接口，不直接依赖具体厂商 SDK。

### 7.2 配置

```yaml
llm:
  enabled: false
  provider: deepseek
  base_url: ""
  api_key: "${LLM_API_KEY}"
  model: ""
  timeout: 30s
  max_tokens: 1200
  temperature: 0.2
```

API Key 只能通过环境变量或部署密钥注入，不允许写入前端或提交到仓库。

### 7.3 调用流程

```text
新增/修改跟进记录
        ↓
业务数据先保存成功
        ↓
创建 AI 分析任务
        ↓
读取客户、跟进和商机上下文
        ↓
调用大模型
        ↓
校验结构化结果
        ↓
保存分析历史
        ↓
更新客户当前意向
```

一期允许提供手动同步分析接口；自动触发使用异步任务，避免阻塞跟进保存。

## 8. 接口与权限

建议接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/crm/customer/:id/intent` | 查询客户当前意向 |
| GET | `/crm/customer/:id/intent/history` | 查询分析历史 |
| POST | `/crm/customer/:id/intent/analyze` | 手动触发分析 |

建议权限：

- `crm:intent:list`
- `crm:intent:analyze`
- `crm:intent:history`
- `crm:intent:config`

所有接口必须沿用当前租户隔离和 CRM 数据权限规则，并记录操作日志。

## 9. 异步任务与失败处理

- 跟进记录保存成功后再投递任务
- Redis 可使用 List 或 Stream 实现任务队列
- 单任务设置超时
- 网络错误和限流错误支持有限次数重试
- JSON 格式错误进入失败状态，不无限重试
- 同一客户同时存在多个任务时，以最新任务结果为准
- AI 服务不可用时，CRM 基础功能保持可用

## 10. 安全与合规

- API Key 不进入前端、不进入日志
- 对外发送数据遵循最小必要原则
- 手机号、邮箱等字段按需要脱敏
- AI 分析数据带 `tenant_id`
- 保留模型、版本、时间和输入快照，便于审计
- AI 结果必须允许人工忽略，不作为自动业务决策的唯一依据

## 11. 实施计划

当前首期已完成：后端配置、数据迁移、OpenAI-compatible Provider、手动分析接口、权限、客户列表展示、分析历史，以及跟进记录保存后的 Redis 异步分析任务。

### 阶段一：基础能力

- 增加 LLM 配置
- 增加意向当前表和历史表
- 增加数据库迁移
- 实现 Provider 抽象和 OpenAI-compatible 适配器
- 提供手动分析接口

### 阶段二：前端能力

- 客户意向结果展示
- 手动分析和重新分析
- 分析历史查看
- 意向等级和分数筛选

### 阶段三：自动化能力

- 跟进记录保存后投递异步任务
- Redis 任务消费
- 超时、重试、失败记录
- 建议跟进提醒

### 阶段四：效果优化

- 分析结果人工反馈
- 模型和 Prompt 版本对比
- 意向转化率统计
- 高意向客户工作台提醒
- 自动生成跟进摘要和沟通话术

### 二期规划：意向结果运营闭环

一期已经完成“调用模型并保存结果”的基础链路。二期目标是让销售可以围绕 AI 意向结果进行筛选、跟进、反馈和复盘，形成可运营的闭环。

#### 11.1 二期目标

- 在客户列表中高效筛选和排序 AI 意向客户。
- 将 AI 建议转化为待跟进任务，减少高意向客户遗漏。
- 支持销售对 AI 结果进行采纳、忽略或人工修正。
- 建立分析成功率、失败原因、人工采纳率和转化结果等基础指标。
- 保持 AI 结果只作为辅助信息，不自动改变客户等级、客户状态和商机阶段。

#### 11.2 功能范围

##### 11.2.1 客户意向筛选与排序

客户列表新增以下查询条件：

- AI 意向等级：高意向、中意向、低意向、未知、未分析。
- 意向分数范围：最低分、最高分。
- 置信度范围：最低置信度。
- 分析状态：未分析、分析中、成功、失败。
- 最近分析时间：最近 7 天、30 天、自定义时间范围。
- 待跟进状态：今日到期、已逾期、未来待跟进、无建议时间。

支持按以下字段排序：

- 意向分数降序。
- 置信度降序。
- 最近分析时间倒序。
- 建议跟进时间正序。

后端客户列表接口应通过数据库关联或子查询完成筛选和排序，避免一期前端逐个请求客户意向造成 N+1 请求。客户列表响应直接返回当前有效意向摘要。

##### 11.2.2 客户意向详情增强

意向详情增加：

- 最近一次分析输入摘要。
- 分析失败原因和重试状态。
- AI 建议跟进时间的逾期标识。
- “采纳建议”“忽略建议”“重新分析”操作。
- 当前结果与上一次结果的变化对比。

历史记录支持分页查询和按状态筛选。失败记录允许手动重试，但应限制单位时间内的重试次数。

##### 11.2.3 人工反馈和修正

销售可以对一次分析结果进行反馈：

- 反馈类型：准确、部分准确、不准确。
- 是否采纳下一步建议。
- 人工修正后的意向等级。
- 人工备注及修正原因。

人工修正不覆盖原始 AI 结果，单独保存反馈记录，并记录操作人、操作时间、租户和原始分析记录 ID。客户列表默认展示 AI 当前结果，同时显示“已人工修正”标识。

##### 11.2.4 待跟进工作台

新增 AI 待跟进视图或销售工作台卡片：

- 高意向客户数量。
- 今日建议跟进数量。
- 已逾期建议跟进数量。
- 最近分析失败数量。
- 最近 7 天意向升高的客户。
- 最近 7 天意向降低的客户。

支持从工作台直接打开客户详情、查看 AI 建议并跳转到跟进记录页面。二期不自动创建真实跟进记录，销售确认后再手动保存跟进内容。

##### 11.2.5 批量分析与任务治理

支持按筛选条件批量提交分析任务：

- 单次批量任务默认最多 50 个客户。
- 相同客户存在未完成任务时不重复入队。
- 任务展示排队中、处理中、成功、失败数量。
- 支持取消尚未开始的任务。
- 失败任务支持有限次数重试。
- 超过重试次数的任务进入失败列表，不能无限循环。

Redis 队列需要增加任务唯一标识和状态记录，并在二期升级为带确认机制的可靠队列：

- 消费者领取任务后进入处理中状态。
- 分析成功后显式确认并删除任务。
- 超时未确认的任务自动重新投递。
- 超过重试次数的任务进入死信列表。
- 服务进程重启后，处理中但未确认的任务可以恢复。

不得继续依赖单纯 `BLPOP` 作为最终可靠投递方案，避免进程异常退出时丢失已取出的任务。

##### 11.2.6 基础运营指标

二期提供基础统计接口和管理页面，至少包含：

- 分析请求总数、成功数、失败数和成功率。
- 平均耗时、P95 耗时。
- 按 Provider、Model、PromptVersion 分组的调用数量。
- 按失败原因分类的数量。
- AI 意向等级分布。
- 人工反馈数量和采纳率。
- 高意向客户的跟进和转化数量。

统计必须支持租户隔离和时间范围查询。金额、转化率等指标需要明确统计口径，不在没有业务数据支撑时虚构结论。

模型效果评估需要单独建立评估口径，至少支持：

- 通过人工标注样本集评估意向等级准确率。
- 对比不同 Provider、Model 和 PromptVersion 的结果。
- 记录人工反馈与 AI 结果的一致率。
- 统计高意向客户后续跟进、商机推进和成交结果。
- 区分模型效果问题、输入数据不足和销售未跟进造成的结果差异。

二期不要求实现模型训练或自动调参，但必须能够沉淀可复核的评估数据。

#### 11.3 二期接口规划

| 方法 | 路径 | 说明 |

| GET | `/crm/customer` | 增加 AI 意向筛选、排序及摘要返回 |
| POST | `/crm/customer/intent/batch` | 按条件批量提交分析 |
| GET | `/crm/customer/intent/tasks/:id` | 查询批量任务进度 |

| GET | `/crm/intent/workbench` | 查询 AI 待跟进工作台数据 |
| GET | `/crm/intent/metrics` | 查询分析和转化基础指标 |

新增接口沿用现有 JWT、权限、租户隔离和操作日志机制。建议新增权限：

- `crm:intent:feedback`
- `crm:intent:batch`
- `crm:intent:workbench`
- `crm:intent:metrics`

##### 11.3.1 配置校验

后端启动时应对关键环境变量和配置进行显式校验：

- MySQL DSN：不能为空，并且必须包含合法数据库路径。
- Redis 地址：不能为空；启用 Redis 时必须校验连接配置。
- LLM 启用时：必须配置 Provider、BaseURL、API Key 和 Model。
- 生产环境必须拒绝开发默认密钥和默认管理员密码。

配置缺失或格式错误时，进程应在连接数据库前直接退出，并明确指出配置项名称、配置来源和修复提示，不应等到 GORM 返回难以理解的原始 DSN 错误。

#### 11.4 二期数据设计

建议新增以下表：

- `crm_customer_intent_feedback`：保存人工反馈、人工修正、采纳状态和修正原因。
- `crm_customer_intent_task`：保存批量分析任务、任务状态、进度和失败统计。
- `crm_customer_intent_task_item`：保存批量任务中的客户、执行状态、重试次数和错误信息。

建议为 `crm_customer_intent` 增加或通过派生查询提供：

- `next_follow_up_status`：待跟进、已逾期、无建议时间。
- `manual_override`：是否存在人工修正。
- `last_analysis_status`：最近一次分析状态。

如果字段只用于查询而不需要持久化，可优先使用查询派生字段，避免重复保存导致状态不一致。

#### 11.5 二期非目标

- 不自动修改 CRM 客户等级、客户状态、商机阶段或合同状态。
- 不自动发送短信、邮件或外部 IM 消息。
- 不在二期实现复杂的模型训练、微调和知识库问答。
- 不以 AI 结果作为唯一的销售考核或客户淘汰依据。
- 不在没有脱敏、权限和审计方案的情况下扩大第三方模型输入范围。

#### 11.6 二期实施顺序

1. 启动配置校验和客户列表 AI 意向筛选、排序及接口性能优化。
2. 可靠 Redis 队列、失败重试、任务状态和批量分析能力。
3. 意向详情增强、结果对比和人工反馈。
4. AI 待跟进工作台和逾期提醒视图。
5. 运营指标、模型效果评估和转化统计。
6. 前端关键流程 E2E 测试及完整验收。

#### 11.6.1 前端 E2E 测试范围

建议使用 Playwright 或同等工具覆盖以下关键流程：

- 登录并进入客户列表。
- 查看客户当前 AI 意向和分析详情。
- 手动触发分析并验证加载、成功和失败提示。
- 查看分析历史。
- 使用 AI 意向等级、分数和待跟进条件筛选客户。
- 提交人工反馈或修正结果。
- 从待跟进工作台跳转客户详情和跟进记录。

E2E 测试应使用独立测试数据和测试环境，不能依赖生产数据或真实模型密钥。

#### 11.7 二期验收标准

- 客户列表可以按 AI 意向等级、分数、分析状态和待跟进状态筛选。
- 客户列表不再为每个客户单独请求一次意向数据。
- 单次最多 50 个客户的批量分析可以查询进度和失败原因。
- 同一客户不会因重复点击产生未完成重复任务。
- AI 分析失败可有限次数重试，失败任务可追踪，超过次数后进入死信列表。
- Redis 消费任务具备确认、超时重投和进程重启恢复能力。
- 销售可以提交人工反馈和人工修正，原始 AI 结果仍可追溯。
- 工作台可以展示高意向、待跟进和逾期客户。
- 统计接口具备租户隔离、时间范围和权限控制，并能区分模型效果与销售跟进结果。
