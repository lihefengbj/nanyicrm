# AI 客户意向分析

## 1. 背景与目标

当前 CRM 已经具备客户、联系人、跟进记录、商机和合同等基础能力。本功能通过调用 DeepSeek、通义千问、智谱、OpenAI 等大模型，结合客户档案、历史跟进和商机信息，判断客户当前意向，辅助销售人员制定下一步跟进计划。

目标：

- 自动识别客户意向等级和意向分数
- 提取客户需求、痛点、预算、采购时间和决策角色
- 识别销售风险
- 生成下一步跟进建议和建议跟进时间
- 保留分析历史，支持追溯、重试和模型效果评估
- 支持切换不同大模型厂商，不让业务代码绑定单一厂商

## 2. 术语与边界

客户现有的 A/B/C 等级与 AI 意向等级含义不同：

| 字段 | 含义 |
| --- | --- |
| 客户等级 | CRM 人工维护的客户分级，A/B/C |
| AI 意向等级 | 基于近期沟通内容动态计算的高/中/低/未知意向 |
| 商机阶段 | 业务人员维护的销售流程阶段 |

AI 只提供判断和建议，不自动修改客户等级、客户状态、商机阶段或合同状态。销售人员可以采纳、忽略或人工修正 AI 建议。

## 3. 一期功能范围

### 3.1 分析触发

- 客户详情页手动触发分析
- 新增或修改跟进记录后触发分析
- 支持重新分析
- AI 调用失败不影响客户和跟进记录保存

### 3.2 分析结果

AI 结果至少包含：

- 意向等级：高意向、中意向、低意向、未知
- 意向分数：0～100
- 置信度：0～1
- 结论摘要
- 客户需求
- 客户痛点
- 预算信息
- 采购时间
- 决策角色
- 销售风险
- 下一步跟进动作
- 建议跟进时间

意向等级建议：

| 等级 | 分数 | 说明 |
| --- | ---: | --- |
| 高意向 | 80～100 | 有明确需求、预算、采购时间或积极推进信号 |
| 中意向 | 50～79 | 有兴趣，但需求、预算或时间尚未明确 |
| 低意向 | 1～49 | 需求较弱、回复少或暂无明确计划 |
| 未知 | 无 | 当前信息不足，无法可靠判断 |

### 3.3 前端展示

客户列表和客户详情支持展示：

- 当前 AI 意向等级
- 意向分数
- 分析摘要
- 最近分析时间
- 建议跟进时间
- 下一步建议
- 分析历史
- 立即分析和重新分析按钮

支持按 AI 意向等级、分数范围和待跟进状态筛选。

## 4. 分析输入

一次分析可以组合以下信息：

- 客户名称、行业、来源、备注
- 联系人姓名、职位
- 最近 5～10 条跟进记录
- 当前商机阶段、金额和预计成交日期
- 最近一次跟进时间
- 当前下次跟进时间

输入内容应限制长度，避免上下文过大和调用成本不可控。建议明确以下输入约束：

- 限制跟进记录条数、单条字符数和整体输入长度。
- 超限时优先保留客户基础信息、最新跟进、当前商机和明确的采购信号，较早的普通跟进可截断或摘要。
- 向模型提供分析基准时间和 `Asia/Shanghai` 时区，保证“几天内跟进”等时间建议可正确转换为北京时间。
- 为输入结构定义版本，并记录输入哈希，便于复现、去重和审计。
- 发送给第三方模型前，对手机号、邮箱、证件号、详细地址及跟进文本中的敏感信息进行脱敏。

## 5. 推荐分析结果结构

```json
{
  "intentLevel": "high",
  "intentScore": 82,
  "confidence": 0.88,
  "summary": "客户已明确表达采购需求，正在比较方案和价格",
  "needs": ["客户管理系统", "销售流程管理"],
  "painPoints": ["客户资料分散", "跟进记录不完整"],
  "budget": "未明确",
  "purchaseTimeline": "预计1个月内",
  "decisionRole": "可能为业务负责人",
  "risks": ["尚未确认预算", "可能存在竞品比较"],
  "nextAction": "3天内安排产品演示并确认预算",
  "suggestedNextAt": "2026-09-21T10:00:00+08:00"
}
```

模型输出必须经过 JSON 解析、字段校验和分值范围校验。无法解析时应标记为分析失败，不得将未经校验的文本直接写入业务字段。

## 6. 数据设计

### 6.1 当前意向表：`crm_customer_intent`

保存客户最新一次有效分析：

- `tenant_id`
- `customer_id`
- `intent_level`
- `intent_score`
- `confidence`
- `summary`
- `needs`
- `pain_points`
- `budget`
- `purchase_timeline`
- `decision_role`
- `risks`
- `next_action`
- `suggested_next_at`
- `analyzed_at`
- `provider`
- `model`
- `prompt_version`
- `status`

列表型和结构化扩展字段一期可使用 JSON 存储；用于筛选、排序的等级和分数使用独立字段。

### 6.2 分析历史表：`crm_customer_intent_analysis`

保存每次分析请求和结果：

- 客户、租户和触发人
- 输入内容快照
- 结构化分析结果
- 分析状态
- 错误信息
- 模型厂商和模型名称
- 实际返回结果所使用的模型
- 模型配置版本和适配器版本
- Prompt 版本
- 生成参数，如 `temperature`、`max_tokens` 和结构化输出模式
- 输入、输出和总 Token 用量
- 厂商请求 ID
- 标准化错误类型
- 输入哈希
- 请求耗时
- 创建时间

历史表用于审计和效果评估，当前意向表用于高效查询。

## 7. 后端架构

### 7.1 Provider 抽象

定义统一的大模型接口：

```go
type LLMProvider interface {
    AnalyzeCustomerIntent(ctx context.Context, input IntentInput) (*IntentResult, error)
}
```

首期使用 OpenAI-compatible HTTP 适配器，通过配置切换 DeepSeek 等兼容厂商。后续如厂商协议不兼容，再增加独立适配器。

业务模块只依赖 Provider 接口，不直接依赖具体厂商 SDK。

### 7.2 配置

```yaml
llm:
  enabled: false
  provider: deepseek
  base_url: ""
  api_key: "${LLM_API_KEY}"
  model: ""
  timeout: 30s
  max_tokens: 1200
  temperature: 0.2
  pricing:
    currency: CNY
    mode: auto
    fixed_period: ""
    timezone: Asia/Shanghai
    holidays: []
    peak_periods:
      - weekdays: [1, 2, 3, 4, 5]
        start: "09:00"
        end: "12:00"
      - weekdays: [1, 2, 3, 4, 5]
        start: "14:00"
        end: "18:00"
    input_cache_hit_idle_per_1m_tokens: 0.02
    input_cache_hit_peak_per_1m_tokens: 0.04
    input_cache_miss_idle_per_1m_tokens: 1
    input_cache_miss_peak_per_1m_tokens: 2
    output_idle_per_1m_tokens: 4
    output_peak_per_1m_tokens: 8
  quota:
    daily_calls: 1000      # 平台默认：每租户每日分析次数上限，0 表示不限制
    daily_tokens: 2000000  # 平台默认：每租户单日Token用量上限，0 表示不限制
    concurrency: 5         # 平台默认：每租户并发分析上限，0 表示不限制
```

`pricing.mode` 支持 `auto`（按时间自动判断）和 `unified`（厂商不区分空闲/高峰）；`pricing.fixed_period` 可选 `idle` 或 `peak`，用于临时强制覆盖。`auto` 使用配置的 `timezone`、`holidays` 和 `peak_periods`；命中 `peak_periods` 的时间为高峰，其余时间为空闲。`peak_periods.weekdays` 使用 Go 的星期编号：周日为 `0`，周一至周六为 `1` 至 `6`；`start` 包含、`end` 不包含，格式为 `HH:MM`。未配置 `peak_periods` 时，默认使用工作日 09:00–12:00、14:00–18:00。周末和 `holidays` 中的日期全天为空闲，即使配置的高峰窗口覆盖这些日期也不会生效。`holidays` 使用 `YYYY-MM-DD`，应按每年国务院公布的法定节假日维护；调休补班的周末仍按周末处理。旧版 `period: idle/peak/unified` 仍可兼容读取。

API Key 只能通过环境变量或部署密钥注入，不允许写入前端或提交到仓库。

`llm.quota` 是平台级默认额度；管理员可在租户管理页为单个租户设置覆盖值（留空继承平台默认，0 表示不限制）。每日分析次数与 Token 用量按天在 Redis 中计数（键含日期与租户，跨天自动失效），并发数以数据库中在途分析记录统计。达到阈值时停止创建新任务并提示：手动分析与批量提交被直接拒绝，跟进触发的后台分析跳过入队并记录日志；已在队列中的任务在执行时若额度已耗尽，以非可重试错误失败并在任务明细中展示原因。管理员可在租户管理页查看各租户今日用量并重置计数。

### 7.3 调用流程

```text
新增/修改跟进记录
        ↓
业务数据先保存成功
        ↓
创建 AI 分析任务
        ↓
读取客户、跟进和商机上下文
        ↓
调用大模型
        ↓
校验结构化结果
        ↓
保存分析历史
        ↓
更新客户当前意向
```

一期允许提供手动同步分析接口；自动触发使用异步任务，避免阻塞跟进保存。

手动分析需要统一前端、网关和后端模型调用的超时策略。前端等待时间不得短于服务端模型超时；如果预计分析时间无法稳定控制在交互超时内，应改为提交异步任务并由前端轮询状态，避免模型仍在执行但页面已经提示失败。

### 7.4 模型治理与切换

二期只支持部署级全局模型配置，不承诺租户在页面中在线切换模型。模型切换不能只替换 `provider`、`base_url` 和 `model`，还应建立以下治理机制：

- 模型能力配置：记录模型是否支持结构化输出、`response_format`、思考模式、最大上下文、最大输出长度及可用生成参数。
- 切换前验证：执行连通性检查、鉴权检查、模型存在性检查和最小结构化输出测试。
- 固定样本评估：使用脱敏且版本固定的客户样本集，对意向等级准确率、字段完整率、JSON 解析成功率、延迟和成本进行对比。
- 评分校准：不同模型的 0～100 分数不得默认视为同一尺度，应检查意向等级分布、分数分布和人工反馈一致率是否发生明显漂移。
- 灰度与回滚：模型配置应有版本号，支持按小比例任务灰度验证；异常时可以快速回滚到上一有效配置。
- 操作审计：记录配置变更人、变更时间、变更前后内容、验证结果及回滚原因，密钥只记录引用或脱敏值。

每次分析历史必须固化实际 Provider、实际模型、模型配置版本、适配器版本和 Prompt 版本，避免模型切换后无法解释历史结果。

## 8. 接口与权限

建议接口：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/crm/customer/:id/intent` | 查询客户当前意向 |
| GET | `/crm/customer/:id/intent/history` | 查询分析历史 |
| POST | `/crm/customer/:id/intent/analyze` | 手动触发分析 |

建议权限：

- `crm:intent:list`
- `crm:intent:analyze`
- `crm:intent:history`
- `crm:intent:config`

所有接口必须沿用当前租户隔离和 CRM 数据权限规则，并记录操作日志。

## 9. 异步任务与失败处理

- 跟进记录保存成功后再投递任务
- Redis 可使用 List 或 Stream 实现任务队列
- 单任务设置超时
- 网络超时、连接失败、厂商 5xx 和限流错误属于可重试错误，使用有限次数的指数退避重试
- 鉴权失败、模型不存在、请求参数不兼容和持续 JSON 校验失败属于不可自动重试错误，应直接记录并告警
- JSON 格式错误可在明确限制内进行一次结构修复或重试，仍不合法则进入失败状态
- 同一客户同时存在多个任务时，以“最新触发任务”的结果为准，而不是以“最后完成任务”的结果为准
- 当前意向更新时校验任务序号、分析记录 ID 或输入版本，旧任务即使较晚完成也不得覆盖新结果
- AI 服务不可用时，CRM 基础功能保持可用

## 10. 安全与合规

- API Key 不进入前端、不进入日志
- 对外发送数据遵循最小必要原则
- 手机号、邮箱等结构化字段以及跟进文本中的敏感信息按需要脱敏
- AI 分析数据带 `tenant_id`
- 保留模型、版本、时间和输入快照，便于审计
- 输入快照、模型输出和人工反馈采用与 CRM 客户数据一致的权限控制，禁止跨租户读取
- 明确输入快照和模型原始响应的保存期限、归档与删除策略；客户数据删除或匿名化时同步处理相关 AI 数据
- 应用日志不得记录 API Key、完整客户输入、完整模型响应和未经脱敏的第三方错误正文
- 生产环境的 BaseURL 必须使用 HTTPS，并支持配置厂商域名白名单或禁止访问内网地址，降低错误配置和服务端请求伪造风险
- AI 结果必须允许人工忽略，不作为自动业务决策的唯一依据

- 增加意向当前表和历史表

### 阶段二：前端能力

- 高意向客户工作台提醒
- 自动生成跟进摘要和沟通话术

### 二期规划：意向结果运营闭环

一期已经完成“调用模型并保存结果”的基础链路。二期目标是让销售可以围绕 AI 意向结果进行筛选、跟进、反馈和复盘，形成可运营的闭环。

#### 11.1 二期目标

- 在客户列表中高效筛选和排序 AI 意向客户。
- 将 AI 建议转化为待跟进任务，减少高意向客户遗漏。
- 支持销售对 AI 结果进行采纳、忽略或人工修正。
- 建立分析成功率、失败原因、人工采纳率和转化结果等基础指标。
- 保持 AI 结果只作为辅助信息，不自动改变客户等级、客户状态和商机阶段。

#### 11.2 功能范围

##### 11.2.1 客户意向筛选与排序

客户列表新增以下查询条件：

- AI 意向等级：高意向、中意向、低意向、未知、未分析。
- 意向分数范围：最低分、最高分。
- 置信度范围：最低置信度。
- 分析状态：未分析、分析中、成功、失败。
- 最近分析时间：最近 7 天、30 天、自定义时间范围。
- 待跟进状态：今日到期、已逾期、未来待跟进、无建议时间。

支持按以下字段排序：

- 意向分数降序。
- 置信度降序。
- 最近分析时间倒序。
- 建议跟进时间正序。

后端客户列表接口应通过数据库关联或子查询完成筛选和排序，避免一期前端逐个请求客户意向造成 N+1 请求。客户列表响应直接返回当前有效意向摘要。

##### 11.2.2 客户意向详情增强

意向详情增加：

- 最近一次分析输入摘要。
- 分析失败原因和重试状态。
- AI 建议跟进时间的逾期标识。
- “采纳建议”“忽略建议”“重新分析”操作。
- 当前结果与上一次结果的变化对比。
- 最近一次人工反馈摘要，包括反馈结论、是否采纳建议、人工修正等级、备注、提交人和提交时间。
- 可展开查看完整人工反馈历史，并明确每条反馈对应的原始 AI 分析记录。

历史记录支持分页查询和按状态筛选。失败记录允许手动重试，但应限制单位时间内的重试次数。

##### 11.2.3 人工反馈和修正

销售可以对一次分析结果进行反馈：

- 反馈类型：准确、部分准确、不准确。
- 是否采纳下一步建议。
- 人工修正后的意向等级。
- 人工备注及修正原因。

人工修正不覆盖原始 AI 结果，单独保存反馈记录，并记录操作人、操作时间、租户和原始分析记录 ID。客户列表默认展示 AI 当前结果，同时显示“已人工修正”标识。

产品展示和统计必须区分三个口径：

- 原始 AI 意向：模型本次分析直接产生的等级和分数，用于模型效果评估。
- 人工修正意向：销售对指定分析记录提交的修正等级，用于业务判断和审计。
- 当前有效意向：列表、筛选和工作台实际采用的业务口径；存在有效人工修正时优先使用人工修正，否则使用最新有效 AI 意向。

页面应同时保留原始 AI 结果和人工修正结果，不能只展示修正后的结论。重新分析产生新记录后，默认将上一条分析记录上的人工修正标记为历史反馈，不自动覆盖新分析；新结果需要重新确认或提交新的人工修正。若未来允许人工修正在多次分析间持续生效，应提供明确的有效期和撤销操作，并完整记录变更历史。

人工反馈提交后应立即在意向详情中回显。用户关闭并重新打开意向详情时，系统必须重新查询已保存的反馈记录，默认展示最近一次反馈，并允许查看完整反馈历史，避免用户误以为反馈或备注未保存。

反馈历史至少展示：

- 反馈类型：准确、部分准确、不准确。
- 是否采纳下一步建议。
- 人工修正后的意向等级。
- 人工备注及修正原因。
- 提交人和提交时间。
- 对应的 AI 分析记录及分析时间。

人工反馈属于审计和模型效果评估数据，已提交记录默认不允许前端直接覆盖。后续如需支持修改或撤销，应保留变更历史，不能通过更新原记录丢失审计信息。

##### 11.2.4 待跟进工作台

新增 AI 待跟进视图或销售工作台卡片：

- 高意向客户数量。
- 今日建议跟进数量。
- 已逾期建议跟进数量。
- 最近分析失败数量。
- 最近 7 天意向升高的客户。
- 最近 7 天意向降低的客户。

支持从工作台直接打开客户详情、查看 AI 建议并跳转到跟进记录页面。二期不自动创建真实跟进记录，销售确认后再手动保存跟进内容。

##### 11.2.5 批量分析与任务治理

支持按筛选条件批量提交分析任务：

- 单次批量任务默认最多 50 个客户。
- 相同客户存在未完成任务时不重复入队。
- 任务展示排队中、处理中、成功、失败数量。
- 支持取消尚未开始的任务。
- 失败任务支持有限次数重试。
- 超过重试次数的任务进入失败列表，不能无限循环。
- 按租户配置同时执行任务数、单位时间提交量和每日分析额度。
- 支持配置单日 Token 或费用上限，达到阈值时停止创建新任务并提示管理员。

Redis 队列需要增加任务唯一标识和状态记录，并在二期升级为带确认机制的可靠队列：

- 消费者领取任务后进入处理中状态。
- 分析成功后显式确认并删除任务。
- 超时未确认的任务自动重新投递。
- 超过重试次数的任务进入死信列表。
- 服务进程重启后，处理中但未确认的任务可以恢复。

不得继续依赖单纯 `BLPOP` 作为最终可靠投递方案，避免进程异常退出时丢失已取出的任务。

##### 11.2.6 基础运营指标

二期提供基础统计接口和管理页面，至少包含：

- 分析请求总数、成功数、失败数和成功率。
- 平均耗时、P95 耗时。
- 按 Provider、Model、PromptVersion 分组的调用数量。
- 按模型配置版本和适配器版本分组的调用数量及结果差异。
- 输入 Token、输出 Token、总 Token 和预估费用。
- 按失败原因分类的数量。
- AI 意向等级分布。
- 人工反馈数量和采纳率。
- 高意向客户的跟进和转化数量。

统计必须支持租户隔离和时间范围查询。金额、转化率等指标需要明确统计口径，不在没有业务数据支撑时虚构结论。

“采纳下一步建议”只表示销售认可建议，不代表已经完成电话、拜访或创建了真实跟进记录。运营指标应分别统计建议采纳、跟进记录创建、商机推进和最终转化，禁止将采纳率直接作为执行率或转化率。

模型效果评估需要单独建立评估口径，至少支持：

- 通过人工标注样本集评估意向等级准确率。
- 对比不同 Provider、Model 和 PromptVersion 的结果。
- 对比模型切换前后固定样本和线上反馈的等级分布、分数分布、解析成功率、延迟和成本。
- 记录人工反馈与 AI 结果的一致率。
- 统计高意向客户后续跟进、商机推进和成交结果。
- 区分模型效果问题、输入数据不足和销售未跟进造成的结果差异。

二期不要求实现模型训练或自动调参，但必须能够沉淀可复核的评估数据。

##### 11.3.1 配置校验

后端启动时应对关键环境变量和配置进行显式校验：

- MySQL DSN：不能为空，并且必须包含合法数据库路径。
- Redis 地址：不能为空；启用 Redis 时必须校验连接配置。
- LLM 启用时：必须配置 Provider、BaseURL、API Key 和 Model。
- 根据 Provider 和 Model 能力矩阵校验 `response_format`、思考模式、上下文长度、`max_tokens` 和其他生成参数是否兼容。
- 提供独立的 LLM 配置测试能力，至少验证网络连通、鉴权、模型可用和结构化 JSON 输出，不以“配置项非空”代替真实可用性检查。
- 生产环境必须拒绝开发默认密钥和默认管理员密码。

配置缺失或格式错误时，进程应在连接数据库前直接退出，并明确指出配置项名称、配置来源和修复提示，不应等到 GORM 返回难以理解的原始 DSN 错误。

#### 11.4 二期数据设计

建议新增以下表：

- `crm_customer_intent_feedback`：保存人工反馈、人工修正、采纳状态和修正原因。
- `crm_customer_intent_task`：保存批量分析任务、任务状态、进度和失败统计。
- `crm_customer_intent_task_item`：保存批量任务中的客户、执行状态、重试次数和错误信息。

`crm_customer_intent_feedback` 查询应支持按租户、客户和分析记录过滤，并按提交时间倒序分页。建议建立 `(tenant_id, customer_id, created_at)` 联合索引；查询响应应关联用户表返回提交人名称，但不得向前端暴露不必要的用户敏感字段。

建议为 `crm_customer_intent` 增加或通过派生查询提供：

- `next_follow_up_status`：待跟进、已逾期、无建议时间。
- `manual_override`：是否存在人工修正。
- `last_analysis_status`：最近一次分析状态。
- `latest_analysis_id` 或等价任务版本字段：标识最新触发且允许更新当前意向的分析，防止旧任务晚完成后覆盖新结果。

建议为 `crm_customer_intent_analysis` 增加或明确以下字段：

- `model_config_version`：本次调用采用的模型配置版本。
- `adapter_version`：Provider 适配器版本。
- `actual_model`：厂商实际执行并返回的模型。
- `input_tokens`、`output_tokens`、`total_tokens`：Token 使用量。
- `provider_request_id`：厂商请求 ID，便于问题排查。
- `error_type`：标准化错误分类，如超时、限流、鉴权、模型不存在、结构校验失败。
- `input_hash`：规范化输入哈希，用于审计、去重和结果复现。

如果字段只用于查询而不需要持久化，可优先使用查询派生字段，避免重复保存导致状态不一致。

#### 11.5 二期非目标

- 不自动修改 CRM 客户等级、客户状态、商机阶段或合同状态。
- 不自动发送短信、邮件或外部 IM 消息。
- 不在二期实现复杂的模型训练、微调和知识库问答。
- 不以 AI 结果作为唯一的销售考核或客户淘汰依据。
- 不在没有脱敏、权限和审计方案的情况下扩大第三方模型输入范围。

#### 11.6 二期实施顺序

1. 启动配置校验、模型能力配置和 LLM 连通性及结构化输出测试。
2. 建立固定脱敏样本集、质量基线、模型配置版本、切换审计和回滚能力。
3. 客户列表 AI 意向筛选、排序及接口性能优化。
4. 可靠 Redis 队列、失败分类、重试、任务状态、并发版本控制和批量分析能力。
5. 意向详情增强、结果对比、有效意向口径和人工反馈。
6. AI 待跟进工作台和逾期提醒视图。
7. Token、成本、运营指标、模型效果评估和转化统计。

#### 11.6.1 前端 E2E 测试范围

建议使用 Playwright 或同等工具覆盖以下关键流程：

- 登录并进入客户列表。
- 查看客户当前 AI 意向和分析详情。
- 手动触发分析并验证加载、成功和失败提示。
- 验证同步分析超时与异步任务降级流程。
- 查看分析历史。
- 使用 AI 意向等级、分数和待跟进条件筛选客户。
- 提交人工反馈或修正结果。
- 提交反馈后立即显示最新反馈和备注。
- 关闭并重新打开意向详情后，仍能查看最近反馈及完整反馈历史。
- 从待跟进工作台跳转客户详情和跟进记录。
- 验证限流、鉴权失败、模型不存在、请求参数不兼容和 JSON 校验失败时的错误提示与重试规则。
- 验证模型配置切换、灰度和回滚后，页面展示的实际模型及配置版本正确。
- 并发触发同一客户的两次分析，验证旧任务晚完成时不会覆盖新任务结果。

E2E 测试应使用独立测试数据和测试环境，不能依赖生产数据或真实模型密钥。

#### 11.7 二期验收标准

- 客户列表可以按 AI 意向等级、分数、分析状态和待跟进状态筛选。
- 客户列表不再为每个客户单独请求一次意向数据。
- 单次最多 50 个客户的批量分析可以查询进度和失败原因。
- 同一客户不会因重复点击产生未完成重复任务。
- AI 分析失败可有限次数重试，失败任务可追踪，超过次数后进入死信列表。
- Redis 消费任务具备确认、超时重投和进程重启恢复能力。
- 销售可以提交人工反馈和人工修正，原始 AI 结果仍可追溯。
- 人工反馈提交后可立即回显；重新打开意向详情后仍可查看备注、提交人、提交时间及对应分析记录。
- 人工反馈历史支持租户隔离和分页查询，其他租户无法读取反馈记录。
- 工作台可以展示高意向、待跟进和逾期客户。
- 统计接口具备租户隔离、时间范围和权限控制，并能区分模型效果与销售跟进结果。
- 后端缺失关键环境变量时能在启动前输出明确配置错误。
- LLM 配置能够校验模型参数兼容性，并通过连通性、鉴权和结构化输出测试后才允许启用。
- 按租户配置每日分析次数、单日 Token 与并发上限，达到阈值时停止创建新任务并给出明确提示。
- 跟进保存触发的后台分析在额度耗尽时跳过入队，不影响跟进记录保存。
- 平台管理员可查看各租户今日额度使用情况并重置计数，超限原因可追溯。
- 模型切换具备固定样本质量门禁、配置版本、变更审计、灰度验证和一键回滚能力。
- 不同模型切换前后可以对比等级分布、分数分布、人工反馈一致率、解析成功率、延迟和成本。
- 同一客户并发分析时，旧任务不能覆盖最新触发任务的结果。
- 统计可以按 Provider、实际 Model、模型配置版本和错误类型查询 Token、成本、成功率及耗时。
- 输入快照、模型响应和人工反馈具备租户隔离、权限控制、脱敏、日志保护及生命周期管理。
- 前端、网关和后端分析超时策略一致；超过交互时限的分析采用可查询状态的异步流程。
- 前端关键 AI 流程具备可重复执行的 E2E 测试。
- `go test ./...`、`go vet ./...`、`go build ./...`、`pnpm build` 和 E2E 测试通过。

#### 11.8.1 AI 意向分析测试数据

已增加后端测试数据生成命令：

```powershell
cd backend
go run ./cmd/seed-intent-data
```

命令从本机环境变量读取数据库、Redis 和大模型配置，不在代码或日志中保存密钥。默认租户为 `1`、负责人用户为 `1`，也可以通过以下环境变量调整：

- `SEED_TENANT_ID`
- `SEED_OWNER_ID`

默认生成 30 个客户，名称统一使用 `AI测试客户-` 前缀，覆盖高意向、中意向、低意向和未知意向四类样本，并生成联系人、跟进记录和部分商机。命令可重复执行，已存在的测试客户会复用，不重复创建。

如果需要清理并重新生成本命令创建的测试数据，可显式设置：

```powershell
$env:SEED_RESET = "true"
go run ./cmd/seed-intent-data
```

`SEED_RESET=true` 只清理当前租户下名称以 `AI测试客户-` 开头的测试数据，默认不执行清理。生成数据后，可在客户列表搜索 `AI测试客户-`，逐个或批量执行 AI 意向分析。

#### 11.9 三期规划：提示词动态配置与模型切换治理

一期把系统提示词硬编码在 `internal/ai/provider.go`，二期已固化 `prompt_version` 字段（当前意向表、分析历史表及工作台指标均已按版本分组）。三期目标是把提示词升级为受治理的动态配置，并补齐 7.4 节"模型切换治理"中尚未实现的固定样本评估、评分校准、变更审计、灰度和回滚能力。

##### 11.9.1 目标与边界

- 提示词文本由硬编码迁出，最终以数据库管理，支持版本历史、质量门禁、灰度发布和一键回滚。
- 延续 7.4 的部署级全局口径：不开放租户在线切换模型或提示词，灰度仅作为发布验证手段。
- 输出契约（JSON 结构、字段名、`intentLevel` 枚举、0～100 分数、0～1 置信度）始终由代码持有并强校验；可配置的仅限"研判段"（等级定义、评分锚点、提取标准、输出详略与示例），不得改变契约字段。
- 租户级调用额度与成本上限不在本方案内，仍按 11.8 进度表独立推进；不涉及模型训练或微调。

##### 11.9.2 数据设计

提示词表 `sys_ai_prompt`：

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| name | 版本名称，便于识别（如"意向研判口径 v3"） |
| content | 研判段提示词全文 |
| content_hash | `content` 规范化后的 SHA-256 摘要，版本号唯一来源 |
| version | 由 `content_hash` 派生的版本号（如 `v3f2a1b9c`），不可重复 |
| status | draft 草稿 / approved 已过门禁 / active 激活中 / retired 已下线 |
| enabled_at / retired_at | 激活与下线时间 |
| created_by / updated_by / created_at / updated_at | 审计字段 |

提示词变更审计表 `sys_ai_prompt_change`：

- 记录变更类型（创建/编辑/门禁/激活/回滚）、变更前后内容、操作人、时间、门禁验证结果摘要与回滚原因。
- 历史版本行只读不可变；回滚不修改旧记录，而是把目标历史版本重新激活。

规则：

- 版本号由内容哈希派生，内容一变版本必变，杜绝"改了内容忘记升版本"。
- 同一时刻至多一个 `active` 版本；激活动作需先通过门禁，并写入审计。
- 每次分析继续固化 `prompt_version`，历史结果不因配置切换失去解释。

##### 11.9.3 固定样本质量门禁

- 复用 `cmd/seed-intent-data` 的固定样本集（30 个客户，覆盖高/中/低/未知四类）作为提示词与模型配置共用的评估基准。
- 候选提示词通过门禁才允许进入 `approved`，未通过禁止激活，门禁指标：
  - JSON 解析成功率 100%；
  - 枚举与字段合法率 100%（复用 `validateIntentResult` 口径）；
  - 字段完整率不低于可配置阈值；
  - 延迟与 Token 成本，与当前激活版本对比。
- 门禁结果摘要写入 `sys_ai_prompt_change`，作为审计依据。

##### 11.9.4 灰度发布与一键回滚

- 灰度：按租户或按任务比例把新版本路由到少量分析任务，队列任务记录目标 `prompt_version`；观察窗口内对比解析成功率、失败类型分布与意向等级分布。
- 回滚：观察指标异常或人工确认失败时，将上一个已通过门禁的版本重新置为 `active` 并立即生效（运行时从数据库重载，无需重启），回滚动作记录操作人与原因。

##### 11.9.5 评分校准看板

- 按 `prompt_version`、`model_config_version`、Provider、实际模型分组对比：意向等级分布、分数分布、人工反馈一致率、JSON 解析成功率、延迟与成本。
- 工作台"意向升降"等跨期统计按版本分段展示或在切换点标注，避免不同评分尺度的结果被直接比较而误导销售。
- 等级分布出现显著漂移时告警，作为回滚决策输入。

##### 11.9.6 接口与权限（仅平台管理员）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/system/ai/prompt` | 提示词版本列表 |
| POST | `/api/v1/system/ai/prompt` | 新建草稿 |
| PUT | `/api/v1/system/ai/prompt/:id` | 编辑草稿 |
| POST | `/api/v1/system/ai/prompt/:id/approve` | 执行固定样本质量门禁 |
| POST | `/api/v1/system/ai/prompt/:id/activate` | 激活版本（可带灰度比例参数） |
| POST | `/api/v1/system/ai/prompt/:id/rollback` | 回滚到上一个已过门禁版本 |
| GET | `/api/v1/system/ai/prompt/:id/changes` | 变更与审计历史 |

- 权限点建议 `system:ai:prompt:*`，仅 superAdmin / admin 可用（沿用 `RequirePrivileged`）；全部写操作进入操作日志。

##### 11.9.7 与现有实现的联动点

- 分析去重键由 `input_hash` 升级为 `input_hash + prompt_version`（含模型配置版本），保证提示词变更后同一输入允许重新分析，避免新口径对存量客户永不生效。
- 当前意向表、分析历史表、工作台指标继续固化并展示 `prompt_version`；版本切换点在指标页标注。
- 提示词版本与输入版本（`input_version`）、输入哈希语义正交，互不影响。
- 校验失败继续走既有 `result_validation` 错误分类；发布后以失败率突变作为门禁之外的补充观测信号。

##### 11.9.8 实施顺序

1. 提示词从硬编码迁出：契约段保留在代码，研判段移入配置（内容哈希版本、启动校验、去重键联动）。
2. 固定样本质量门禁与候选测试通道（复用 ConfigTest 机制）。
3. 提示词与变更审计落库、管理端页面与接口、激活/回滚闭环。
4. 按租户或任务比例的灰度与观察窗口。
5. 评分校准看板与跨版本对比指标。

##### 11.9.9 三期验收标准

- 提示词修改必须通过门禁（JSON 解析率、枚举合法率、字段完整率）才能激活。
- 任一版本的内容、哈希、版本号、操作人与时间可追溯，旧版本不可变。
- 灰度期间新旧版本并存，任务与分析记录可区分所属版本。
- 支持一键回滚且不丢失历史版本，回滚动作有审计记录。
- 校准看板可按版本对比等级/分数分布、人工反馈一致率、解析成功率、延迟与成本。
- 提示词切换后，同一客户同输入可重新分析，去重不吞掉新版本任务。
- 仅平台管理员可管理提示词，租户用户无提示词管理入口。
